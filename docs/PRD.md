## 1. Overview

SCWL is a web application for running a distribution network: managing suppliers, products, warehouse stock, carriers and shipments, with live inventory visibility and end-to-end shipment tracking.

The database (MySQL, `supply_chain`) and ER model already exist. This PRD defines the **frontend and backend** that sit on top of that schema, structured like the reference project **EcoTrack** (`Parth-Pingle10/ecotrack`): a Vite + React + TypeScript + Tailwind + shadcn/ui frontend at the repo root (`src/`, `public/`) and a separate `backend/` folder.

> Note: I could read EcoTrack's root files and `package.json`, but GitHub blocked automated access to its `backend/` folder. The backend choices below are therefore my recommendation, not a copy of EcoTrack's backend. Swap in whatever EcoTrack uses if it differs.

## 2. Problem Statement

Warehouse staff and logistics managers need to (a) see accurate stock per warehouse, (b) be warned before stock runs out, (c) dispatch goods via carriers, and (d) track each shipment from warehouse to destination. Today this exists only as SQL tables and views, with no usable interface, no access control and no enforced business workflow.

## 3. Goals and Non-Goals

**Goals**
1. Full CRUD for all master data (suppliers, products, warehouses, carriers).
2. Real-time inventory per warehouse with low-stock alerts.
3. Shipment creation, dispatch and delivery workflow that keeps inventory correct.
4. Public-facing tracking timeline per shipment.
5. Dashboard with KPIs and charts.
6. Role-based access (Admin, Warehouse Manager, Logistics Coordinator, Viewer).

**Non-goals (v1)**
- Payments, invoicing, customer orders/e-commerce.
- Live GPS or carrier API integration (tracking logs are entered manually or by a simulated feed).
- Mobile native apps (responsive web only).
- Multi-tenant / multi-company support.

## 5. Data Model (existing schema)

Nine tables, as implemented in `supply_chain.sql`:

| Table | Key | Notes |
|---|---|---|
| Suppliers | `supplier_id` | `contact_email` UNIQUE |
| Products | `product_id` | `sku` UNIQUE, `unit_price >= 0` |
| Warehouses | `warehouse_id` | `max_capacity > 0` |
| Carriers | `carrier_id` | `vehicle_type` |
| Supplier_Product | (`supplier_id`, `product_id`) | M:N bridge, cascade delete |
| Inventory_Levels | (`product_id`, `warehouse_id`) | `quantity_on_hand >= 0`, `reorder_threshold >= 0` |
| Shipments | `shipment_id` | FK warehouse, FK carrier, `current_status` default `Pending` |
| Shipment_Items | (`shipment_id`, `product_id`) | `quantity_shipped > 0` |
| Shipment_Logs | (`shipment_id`, `log_id`) | `log_id` is the partial key; `logged_at` required |

**Existing views to reuse directly as read endpoints:** `vw_Warehouse_Inventory`, `vw_Low_Stock_Alerts`, `vw_Shipment_Details`, `vw_Shipment_Tracking`, `vw_Supplier_Catalog`.

### 5.1 Schema gaps to fix for the app (small, additive)

The project works as a DB demo, but a real app needs these. All are backward compatible.

| # | Change | Why |
|---|---|---|
| 1 | `AUTO_INCREMENT` on all single-column PKs (`supplier_id`, `product_id`, `warehouse_id`, `carrier_id`, `shipment_id`) | The API cannot ask users to type IDs. Keep the existing seed IDs. |
| 2 | `log_id` generated by backend as `MAX(log_id)+1` per shipment, inside a transaction | Partial key per shipment |
| 3 | New `Users` table (`user_id`, `name`, `email` UNIQUE, `password_hash`, `role`, `warehouse_id` NULL, `created_at`) | Authentication and RBAC |
| 4 | New `Stock_Movements` table (`movement_id`, `product_id`, `warehouse_id`, `change_qty`, `reason` ENUM(`RECEIPT`,`DISPATCH`,`ADJUSTMENT`,`RETURN`), `shipment_id` NULL, `user_id`, `created_at`) | Audit trail for every stock change |
| 5 | Replace free-text `current_status` with `ENUM('Pending','Dispatched','In Transit','Delivered','Cancelled')` | Valid state machine. Seed data already fits these values, except log entries use `Order Received` (log text only, so no conflict). |
| 6 | Add `created_at`, `dispatched_at`, `delivered_at` to `Shipments` | Lead-time reporting |
| 7 | Add `CHECK` or trigger: total `quantity_on_hand` per warehouse <= `max_capacity` | `max_capacity` is currently never enforced |
| 8 | Optional: `supplier_price` and `lead_time_days` on `Supplier_Product` | Meaningful supplier comparison |
| 9 | Indexes on `Shipments(current_status)`, `Shipments(warehouse_id)`, `Shipment_Logs(shipment_id, logged_at)` | List and tracking performance |

Observation worth knowing: in the seed data, shipped quantities (e.g. shipment 401 sent 20 laptops from warehouse 201) were not subtracted from `Inventory_Levels`. The backend will enforce this going forward (see section 7).

## 9. Backend API Specification

Base URL `/api/v1`. JSON in and out. Auth via `Authorization: Bearer <token>`. Errors use `{ "error": { "code": "...", "message": "...", "details": [...] } }`. List endpoints accept `?q=&page=&limit=&sort=`.

### 9.2 Example: create shipment

```http
POST /api/v1/shipments
{
  "warehouse_id": 201,
  "carrier_id": 301,
  "destination_address": "Andheri East, Mumbai",
  "items": [
    { "product_id": 101, "quantity_shipped": 20 },
    { "product_id": 102, "quantity_shipped": 15 }
  ]
}
→ 201 { "shipment_id": 405, "current_status": "Pending", ... }
```

Validation: each product must have an `Inventory_Levels` row in that warehouse with enough stock (checked at creation as a warning, enforced at dispatch).

### 9.3 Dispatch transaction (core business rule)

```
BEGIN;
  SELECT ... FROM Inventory_Levels WHERE (product_id, warehouse_id) IN (...) FOR UPDATE;
  -- if any quantity_on_hand < quantity_shipped → ROLLBACK, return 409 INSUFFICIENT_STOCK
  UPDATE Inventory_Levels SET quantity_on_hand = quantity_on_hand - ? WHERE ...;
  INSERT INTO Stock_Movements (... 'DISPATCH' ...);
  UPDATE Shipments SET current_status='Dispatched', dispatched_at=NOW() WHERE shipment_id=?;
  INSERT INTO Shipment_Logs (log_id = next, ... 'Dispatched');
COMMIT;
```

`FOR UPDATE` row locks prevent two simultaneous dispatches from overselling the same stock.

### 9.4 Error codes
`400 VALIDATION_ERROR`, `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 DUPLICATE` (SKU/email), `409 INSUFFICIENT_STOCK`, `409 INVALID_STATUS_TRANSITION`, `409 CAPACITY_EXCEEDED`, `409 REFERENCED` (FK blocks delete), `500 INTERNAL`.

## 10. Non-Functional Requirements

| Area | Requirement |
|---|---|
| Performance | List endpoints < 300 ms p95 on up to 100k inventory/shipment rows; paginate everything |
| Security | Parameterized queries only (no string-built SQL), bcrypt hashes, helmet, CORS allow-list, rate limit on login, secrets via `.env`, HTTPS in production |
| Data integrity | All multi-table writes in transactions; DB constraints remain the last line of defence |
| Reliability | Connection pooling; graceful shutdown; health endpoint `/health` |
| Observability | Request logging (pino/morgan), error logging, audit via `Stock_Movements` |
| Testing | Unit tests for services; integration tests for the dispatch transaction and status machine; Vitest on frontend |
| Docs | OpenAPI at `/api/docs`; README with setup in under 10 minutes |
| Compatibility | Latest Chrome, Edge, Firefox, Safari; Node 20+; MySQL 8 |

## 13. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Schema changes break the submitted SQL | Ship changes as numbered migration files; keep original `supply_chain.sql` untouched |
| Overselling under concurrent dispatch | Row locks plus transaction (9.3), covered by an integration test |
| Scope creep (payments, GPS, orders) | Listed as non-goals; P2 items only after P0/P1 |
| Unknown EcoTrack backend conventions | Treat it as visual and structural reference only; confirm backend conventions with the team |
| Auth adds time | If short on time, ship a single seeded Admin login first, then add roles |
